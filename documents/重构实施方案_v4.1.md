# 重构实施方案 v4.1

## 0. 方案摘要

本项目重构为一个以 **React + Vite + TanStack + Drizzle + PostgreSQL** 为基础的全栈 Web App，并作为**一个 Vercel Project**一次性部署：

- **浏览器前端**负责相机采集、二维码读取/生成、图像标准化、OpenCV.js（WASM Worker）ORB 特征提取，以及分享图生成。
- **Vercel Node.js Server Functions**负责凭证预留与激活、数据库访问、特征集读取、服务端独立特征比对、访问控制、密语加密存储与按验证结果解密返回。
- **外部 PostgreSQL**是唯一必需的外部状态服务；通过 Drizzle ORM 管理 schema 和迁移。
- 不部署 Python/FastAPI、Docker、独立图像处理服务、向量数据库或 GPU 服务。

核心原则：二维码用于定位凭证（passcode/token），图像用于二次视觉验证；前端可提取特征，但**最终是否匹配必须由服务端决定**。

---

## 1. 产品目标

项目将一个视觉主体（例如一张埃菲尔铁塔图片或某个现实场景）绑定到一条密语。持有凭证二维码的人，需要提交与参考视觉主体高度一致的图像，才能获取该密语。

示例：

> 创建者拍摄埃菲尔铁塔，将其绑定至密语“明天下午三点老地方见”。
>
> 读取者扫描凭证二维码，系统取得凭证标识；读取者再拍摄或上传埃菲尔铁塔相关图像。系统通过服务端 ORB 特征匹配验证视觉一致性，成功后返回密语。

### 1.1 本次重构目标

1. 建立集中、类型安全、可维护的前后端一体化工程。
2. 使用 React + Vite + TanStack 构建独立 SPA，不依赖 Next.js。
3. 将前端静态资源和后端 Server Functions 以一个 Vercel Project 部署。
4. 使用 OpenCV.js 在浏览器完成图像预处理与 ORB 特征提取。
5. 使用 Vercel Node.js Functions 完成可信的服务端特征匹配与最终授权。
6. 将二维码/URL 凭证与视觉验证分工，降低手动输入与误操作。
7. 以可版本化的特征协议和 Matcher 策略接口支持后续算法演进。
8. 使用一个 PostgreSQL 数据库保存凭证、密语密文、特征集与必要审计数据。

### 1.2 非目标

v4.1 不以以下能力为目标：

- 不实现无 QR、仅凭任意图片在全库中查找对应密语的通用视觉搜索。
- 不将 PostgreSQL/pgvector 作为 ORB descriptor 的全局向量检索引擎。
- 不将二维码与图片分开保存误称为端到端加密或真正去中心化。
- 不将客户端“匹配成功”的结果作为授权依据。
- 不在 Vercel Function 内部使用 OpenCV.js 处理原始大图或做主匹配。

## 2. 总体架构

```text
                    ┌───────────────────────────┐
                    │        浏览器 / SPA         │
                    │ React + Vite + TanStack     │
                    │                             │
                    │  相机 / 上传 / QR 扫描       │
                    │  OpenCV.js Web Worker        │
                    │  预处理 + ORB 特征提取       │
                    └─────────────┬─────────────┘
                                  │ HTTPS：feature payload
                                  ▼
                    ┌───────────────────────────┐
                    │       Vercel Project        │
                    │                             │
                    │ Static SPA / CDN             │
                    │ Node.js Server Functions     │
                    │ - reserve                    │
                    │ - finalize                   │
                    │ - credential lookup          │
                    │ - verify / matcher           │
                    └─────────────┬─────────────┘
                                  │ Drizzle
                                  ▼
                    ┌───────────────────────────┐
                    │   PostgreSQL（唯一外部服务） │
                    │ credentials / feature blobs │
                    │ secret ciphertext / audit    │
                    └───────────────────────────┘
```

### 2.1 职责边界

| 层级 | 职责 | 不负责 |
|---|---|---|
| 浏览器 SPA | 相机采集、文件输入、二维码识别、二维码生成、图像预处理、ORB 提取、特征协议编码、分享图导出、UI 状态 | 最终授权判定、密语解密、数据库直接访问 |
| OpenCV.js Worker | 灰度化、尺寸归一、可选 CLAHE、轻度去噪、QR 区域 mask、ORB keypoints/descriptors 生成 | 网络请求、React UI 渲染、密语逻辑 |
| Vercel Node.js Functions | 输入校验、速率限制、凭证状态检查、读取特征库、Hamming/KNN/ratio/RANSAC 比对、最终放行、密语解密 | 原始图像大规模处理、长任务、全库视觉搜索 |
| PostgreSQL | 凭证、token hash、密语密文、参考图特征 blob、状态、审计数据 | 主计算、实时队列、长期对象存储 |

### 2.2 核心设计决策

1. **一个 Vercel 项目即可部署完整应用。**
   - Vite 构建后的 SPA 作为静态资源部署。
   - `api/` 下的 TypeScript 文件作为 Vercel Node.js Functions。
   - 前端和 API 共享同一 Git 仓库、同一部署流程、同一域名。

2. **前端使用 OpenCV.js，后端实现匹配数学过程。**
   - 前端通过 OpenCV.js Worker 提取 ORB feature payload。
   - 后端以 TypeScript 实现 ORB descriptor 的 Hamming 距离、KNN、Lowe ratio test、可选 mutual check 与 RANSAC homography。
   - 不要求在 Function 中加载浏览器版 OpenCV.js/WASM，因此降低冷启动、包体积、Node 兼容性与内存管理风险。

3. **二维码负责索引，图像负责验证。**
   - QR 先获得 `publicToken` 或 `passcode`，使服务端只加载该凭证的少量候选参考图。
   - 图像匹配用于证明读取者提交的视觉主体与参考图一致。
   - 不做全库 ORB descriptor 检索。

4. **二维码叠加图不作为主参考图。**
   - 原始参考图的 ORB 特征作为主验证依据。
   - 带二维码的分享图仅用于分发，不直接参与主匹配。
   - 若未来支持“拍摄带二维码分享图本身”，另建 `overlay_compatible` 特征集，并在提取前 mask 掉二维码区域。

## 3. 凭证与安全模型

### 3.1 凭证标识设计

用户可见的短 passcode 不应承担全部安全责任。采用双标识：

| 标识 | 用途 | 要求 |
|---|---|---|
| `displayPasscode` | 展示、调试、人工备用输入、二维码中的可读信息 | 可为 10–12 位 Base32/Base62 字符；不可作为唯一安全边界 |
| `publicToken` | URL QR 与主要读取入口中的能力令牌 | 至少 16 byte 的 CSPRNG 随机值，Base64URL 编码；建议约 128 bit 熵 |

生成规则：

```ts
const tokenBytes = crypto.getRandomValues(new Uint8Array(16));
const publicToken = base64UrlEncode(tokenBytes); // 通常约 22 个字符
```

数据库不保存高价值 token 明文：

```text
public_token_hash = HMAC-SHA-256(serverPepper, publicToken)
passcode_hash     = HMAC-SHA-256(serverPepper, displayPasscode)
```

`serverPepper` 仅存在 Vercel 环境变量，不能被写入 `VITE_*` 变量、客户端 bundle、二维码或数据库明文列。

### 3.2 密语保护

- 服务端收到密语后，在写入数据库前使用 AEAD 加密，例如 AES-256-GCM。
- 数据库存储 `secretCiphertext`、`secretIv`、`secretAuthTag`、`secretVersion`。
- 主密钥只保留在 Vercel Environment Variables 或将来的 KMS 中。
- 只有服务端确认图像验证成功后，才解密并返回密语。

该模式是“服务端受控加密存储”，不是端到端加密。若未来需要服务端不可见密语，必须独立设计客户端密钥分发、恢复和撤销机制。

### 3.3 防滥用措施

- 所有 token/passcode 查询都采用固定格式与统一失败响应，降低枚举信息泄露。
- `/api/verify` 必须有请求体大小限制、descriptor 数量限制和速率限制。
- 对同一 token、IP 或匿名会话记录短时失败次数。
- 读取/验证 API 只返回必要结果；失败不暴露匹配分数、参考图数量或凭证是否存在的细节。
- 凭证支持 `active`、`revoked`、`expired` 状态与可选 `expiresAt`。
- 记录审计事件，但避免记录原始图像或精确敏感位置数据。

## 4. 创建流程

### 4.1 创建数据流

```text
进入 Create 页面
  ↓
POST /api/passcodes/reserve
  ↓
服务端生成并预留 displayPasscode + publicToken
  ↓
浏览器拍照或上传原始参考图
  ↓
OpenCV.js Worker：EXIF 纠正、预处理、ORB 特征提取
  ↓
输入密语、选择二维码样式与位置
  ↓
浏览器生成：独立 URL QR + 带 QR 覆盖层的分享图
  ↓
POST /api/credentials/finalize
  ↓
服务端校验预留记录，保存密语密文和参考 feature payload
  ↓
凭证由 reserved → active
```

### 4.2 Passcode 预留

进入创建页面时自动调用：

```http
POST /api/passcodes/reserve
```

服务端：

1. 生成 `displayPasscode` 和 `publicToken`。
2. 计算两者 hash。
3. 插入状态为 `reserved` 的 credential。
4. 设置短暂 TTL，例如 30 分钟。
5. 返回一次性可用于创建流程的 `publicToken` 和展示用 `displayPasscode`。

若用户离开页面或未完成创建，过期预留记录由查询时惰性清理或计划任务清理。MVP 阶段允许惰性清理，不要求额外队列服务。

### 4.3 参考图规范

主参考图必须是**未添加二维码覆盖层**的原图或原始拍摄版本。

建议创建页提示：

- 避免完全无纹理、纯色、严重虚焦、过度压缩图片。
- 尽量保留主体的边缘、结构和局部纹理。
- 对于真实物体或建筑，建议一次创建注册 3–8 张不同角度、距离或光照条件下的参考图。
- 若密语依赖画面中特定物件，应避免该物件在验证时极易被遮挡。

### 4.4 二维码产物

创建成功后在浏览器本地生成并允许下载：

1. **URL QR**：编码为 `https://<domain>/r/<publicToken>`。
2. **带 QR 的分享图**：基于原始图片绘制二维码覆盖层，默认左下角，允许拖拽。

二维码覆盖层参数需要保存为元数据：

```ts
type QrOverlay = {
  x: number;
  y: number;
  width: number;
  height: number;
  coordinateSpace: "normalized";
  quietZone: number;
  version: 1;
};
```

但该分享图不是主 ORB reference。二维码位置、尺寸和样式的变化不应污染主视觉特征库。

## 5. 读取与验证流程

### 5.1 读取数据流

```text
进入 Read 页面或访问 /r/:publicToken
  ↓
相机扫描 QR / URL 中读取 token
  ↓
GET /api/credentials/:publicToken/meta
  ↓
服务端检查 token、凭证状态和可读策略
  ↓
浏览器拍摄或上传待验证图片
  ↓
OpenCV.js Worker：同版本预处理 + ORB 特征提取
  ↓
POST /api/verify
  ↓
Vercel Function：读取候选参考特征集，执行可信匹配
  ↓
匹配成功：解密并返回 secret
匹配失败：返回泛化失败结果
```

### 5.2 QR 读取策略

优先顺序：

1. 扫描 URL QR，直接得到 `publicToken`。
2. 扫描只包含 `displayPasscode` 的 QR 或条码。
3. 仅在失败兜底时允许手动输入 displayPasscode。

实现上：

- 优先使用浏览器 `BarcodeDetector`（可用时）。
- 使用 `zxing-js` 等库作为跨浏览器 fallback。
- QR 识别不依赖 OpenCV.js，降低视觉处理与凭证读取的耦合。

### 5.3 服务端验证算法

后端不能相信客户端发送的“匹配成功”字段；客户端仅提交 query feature payload。服务端执行：

1. 校验 `publicToken` 或 passcode 格式、签名/哈希和 credential 状态。
2. 校验 feature payload 的 schema、版本、尺寸、最大 keypoint 数和二进制长度。
3. 从数据库取该 credential 关联的 1–8 个参考特征集。
4. 对每个参考特征集执行 Hamming KNN matching。
5. 对匹配结果应用 Lowe ratio test。
6. 可选执行 mutual nearest-neighbor check。
7. 在 keypoint 坐标上进行 RANSAC homography 验证。
8. 使用匹配数、RANSAC 内点数、内点率、几何合理性构成最终评分。
9. 任一参考图达到阈值即验证通过；否则统一失败。

推荐成功判定模型：

\[
\text{match} =
(\text{goodMatches} \ge M)
\land
(\text{inliers} \ge I)
\land
\left(\frac{\text{inliers}}{\text{goodMatches}} \ge R\right)
\]

初始实验值可从以下范围开始，再根据真实数据校准：

| 指标 | 建议初值 | 说明 |
|---|---:|---|
| ORB 最大特征数 | 500–1,000 | 控制移动端与函数计算成本 |
| KNN 的 k | 2 | 用于 ratio test |
| Lowe ratio | 0.70–0.80 | 越低越严格 |
| `goodMatches` 最低值 M | 20 | 不应单独作为成功依据 |
| `inliers` 最低值 I | 12 | 几何一致性基础门槛 |
| `inlierRatio` 最低值 R | 0.45 | 排除大量偶然匹配 |

这些不是通用安全阈值。上线前必须用真匹配、错误对象、相似建筑、截图、屏摄、压缩、旋转、低光、遮挡、不同角度和裁剪等样本构建测试集，并以误拒率（FRR）和误接受率（FAR）调参。

## 6. 特征协议与版本化

### 6.1 设计原则

- 不直接 JSON 序列化 OpenCV `Mat`。
- descriptor 与 keypoint 采用紧凑二进制编码。
- 数据库保存二进制 blob，API 传输采用 `multipart/form-data` 或二进制 body；若 MVP 必须 JSON，采用 Base64URL 并严格限制大小。
- 所有影响特征可比性的参数必须进入协议并做版本化。

### 6.2 Feature Payload v1

```ts
export type FeaturePayloadV1 = {
  version: 1;
  algorithm: "orb";
  image: {
    width: number;
    height: number;
    exifOrientationNormalized: true;
  };
  preprocessing: {
    grayscale: true;
    resize: {
      mode: "long-edge";
      target: number;
      interpolation: "area" | "linear";
    };
    clahe?: {
      clipLimit: number;
      tileGrid: [number, number];
    };
    denoise: "none" | "gaussian";
    qrMask?: {
      x: number;
      y: number;
      width: number;
      height: number;
      coordinateSpace: "normalized";
    };
  };
  orb: {
    nFeatures: number;
    scaleFactor: number;
    nLevels: number;
    edgeThreshold: number;
    patchSize: number;
    fastThreshold: number;
    wtaK: 2 | 3 | 4;
  };
  descriptor: {
    rows: number;
    cols: number;
    dtype: "u8";
    bytes: Uint8Array;
  };
  keypoints: {
    count: number;
    xy: Float32Array;
    scale?: Float32Array;
    angle?: Float32Array;
  };
  hashes?: {
    dHash64?: string;
    pHash64?: string;
  };
};
```

要求：

- `descriptor.rows === keypoints.count`。
- `xy.length === keypoints.count * 2`。
- ORB 常见 descriptor 为 `cols = 32`，但服务端必须依据协议字段校验，而不能只硬编码假设。
- query 与 reference 的 `version`、预处理策略和关键 ORB 配置必须可兼容；不兼容时拒绝验证或走明确的 migration 逻辑。

### 6.3 Matcher 策略接口

```ts
export interface MatcherStrategy {
  readonly id: string;
  readonly supportedFeatureVersions: readonly number[];

  match(input: {
    query: FeaturePayloadV1;
    reference: FeaturePayloadV1;
  }): Promise<MatchResult>;
}

export type MatchResult = {
  matched: boolean;
  score: number;
  goodMatchCount: number;
  inlierCount: number;
  inlierRatio: number;
  reason:
    | "matched"
    | "insufficient-features"
    | "ratio-test-failed"
    | "homography-failed"
    | "below-threshold";
};
```

初期实现：

```text
orb-hamming-ransac-v1
```

未来可增加：

```text
phash-prefilter-v1
orb-hamming-ransac-v2
server-opencv-matcher-experimental
```

感知哈希只作为快速拒绝、辅助打分或排序信号，不作为唯一成功依据。

## 7. 数据库设计

### 7.1 数据库选择

使用 PostgreSQL 作为唯一外部数据服务。可选托管方案包括 Neon、Supabase PostgreSQL 或自托管 PostgreSQL。Vercel Server Functions 应使用 serverless/HTTP 适配驱动，避免依赖长生命周期 TCP 连接池。

Drizzle 负责：

- schema 定义
- 类型推导
- migration 生成与执行
- 数据访问层

### 7.2 表结构

```text
credentials
- id UUID PK
- display_passcode_hash TEXT UNIQUE NOT NULL
- display_passcode_hint TEXT NULL
- public_token_hash TEXT UNIQUE NOT NULL
- status TEXT NOT NULL                 -- reserved | active | revoked | expired
- reserve_expires_at TIMESTAMPTZ NULL
- expires_at TIMESTAMPTZ NULL
- secret_ciphertext BYTEA NULL
- secret_iv BYTEA NULL
- secret_auth_tag BYTEA NULL
- secret_version SMALLINT NULL
- created_at TIMESTAMPTZ NOT NULL
- activated_at TIMESTAMPTZ NULL
- revoked_at TIMESTAMPTZ NULL

reference_feature_sets
- id UUID PK
- credential_id UUID FK NOT NULL
- role TEXT NOT NULL                   -- original | overlay_compatible
- feature_version SMALLINT NOT NULL
- matcher_id TEXT NOT NULL
- source_width INT NOT NULL
- source_height INT NOT NULL
- descriptor_count INT NOT NULL
- descriptor_cols INT NOT NULL
- descriptor_bytes BYTEA NOT NULL
- keypoint_xy_bytes BYTEA NOT NULL
- keypoint_scale_bytes BYTEA NULL
- keypoint_angle_bytes BYTEA NULL
- preprocessing_json JSONB NOT NULL
- orb_config_json JSONB NOT NULL
- dhash64 TEXT NULL
- phash64 TEXT NULL
- created_at TIMESTAMPTZ NOT NULL

credential_qr_assets
- id UUID PK
- credential_id UUID FK NOT NULL
- asset_type TEXT NOT NULL             -- url_qr | share_overlay_metadata
- overlay_json JSONB NULL
- created_at TIMESTAMPTZ NOT NULL

verification_attempts
- id UUID PK
- credential_id UUID NULL
- result TEXT NOT NULL                  -- match | no_match | invalid | rate_limited
- matcher_id TEXT NULL
- score NUMERIC NULL
- good_match_count INT NULL
- inlier_count INT NULL
- inlier_ratio NUMERIC NULL
- request_fingerprint_hash TEXT NULL
- created_at TIMESTAMPTZ NOT NULL
```

### 7.3 存储策略

- 不为每一个 ORB descriptor 单独建立 SQL 行。
- 一份 reference feature set 存为一个或少量 `BYTEA` blob。
- 单 reference image 常见数据量通常是几十 KB 到数百 KB；应在创建时限制最大 keypoint 数。
- 按 `public_token_hash` 和 `display_passcode_hash` 建唯一索引。
- 按 `credential_id` 为 `reference_feature_sets` 建普通索引。
- `verification_attempts` 可按时间做保留周期清理，避免无限增长。

## 8. API 设计

### 8.1 `POST /api/passcodes/reserve`

用途：创建页初始化凭证预留。

响应：

```ts
type ReserveResponse = {
  publicToken: string;
  displayPasscode: string;
  reserveExpiresAt: string;
};
```

### 8.2 `POST /api/credentials/finalize`

用途：提交密语与一个或多个主参考 feature payload，激活预留凭证。

请求应包含：

```ts
type FinalizeRequest = {
  publicToken: string;
  secret: string;
  references: FeaturePayloadV1[];
  qrOverlay?: QrOverlay;
};
```

服务端必须：

- 校验该 token 对应记录处于 `reserved` 且未过期。
- 限制密语长度、参考图数量、descriptor 数量和总 payload 大小。
- 校验 feature payload 版本与格式。
- 加密密语。
- 在同一数据库事务中写入 feature sets 并将 credential 更新为 `active`。

### 8.3 `GET /api/credentials/:publicToken/meta`

用途：读取端预检查凭证是否可用。

仅返回必要信息：

```ts
type CredentialMetaResponse = {
  valid: boolean;
  requiresVisualVerification: true;
  featureVersion?: number;
};
```

不要返回密语、参考图、参考特征数量、算法细节或 token 是否精确存在的敏感信息。

### 8.4 `POST /api/verify`

请求：

```ts
type VerifyRequest = {
  publicToken: string;
  query: FeaturePayloadV1;
};
```

成功响应：

```ts
type VerifySuccess = {
  matched: true;
  secret: string;
};
```

失败响应：

```ts
type VerifyFailure = {
  matched: false;
  code: "VERIFICATION_FAILED" | "CREDENTIAL_UNAVAILABLE";
};
```

生产环境不返回细粒度 score、参考图 ID、精确阈值或内部 matcher reason。调试数据仅写入审计表，或仅在开发环境以受控方式返回。

### 9.1 前端状态管理

- TanStack Router：路由与 URL token 路径。
- TanStack Query：reserve、finalize、meta、verify 的 server state、缓存和重试控制。
- TanStack Form：密语、图像选择、二维码覆盖层配置表单。
- 局部组件状态：相机预览、拖拽位置、Worker 处理进度。

### 9.2 OpenCV Worker 原则

- OpenCV.js 只在 Worker 初始化一次。
- 通过消息协议接收 `ImageBitmap`、`Blob` 或 transferable buffers。
- 不在 React render 阶段运行 OpenCV。
- 每次创建的 `cv.Mat`、`cv.KeyPointVector` 等对象必须在 `finally` 中 `delete()`。
- Worker 返回 typed arrays 的 `ArrayBuffer`，尽量使用 transferable 避免复制。
- 使用固定的 `FeaturePayloadV1` 配置，避免创建端与读取端预处理漂移。

## 10. Vercel 部署方案

### 10.1 运行时选择

- API 初期统一使用 **Vercel Node.js Runtime**。
- 不将主验证逻辑首先部署到 Edge Runtime。
- 前端 OpenCV.js/WASM 作为静态资源由 CDN 分发，并在浏览器 Worker 中执行。

### 10.2 环境变量

```text
DATABASE_URL=
TOKEN_PEPPER=
SECRET_ENCRYPTION_KEY=
APP_ORIGIN=
```

规则：

- 仅有 `VITE_*` 前缀变量会被打包给前端。
- `DATABASE_URL`、`TOKEN_PEPPER`、`SECRET_ENCRYPTION_KEY` 不得使用 `VITE_*` 前缀。
- 开发、Preview、Production 使用独立数据库或至少独立 schema/凭证。

### 10.3 `vercel.json` 原则

- 设置 SPA fallback，确保 `/r/:publicToken` 能返回前端入口。
- API 路由由 `api/` 自动识别，不应错误 fallback 到 SPA。
- 对 `/api/verify` 设置适当的最大执行时间和内存配置（具体值依据 Vercel 当前套餐及压测结果确定）。
- 设置安全响应头：`Content-Security-Policy`、`Referrer-Policy`、`X-Content-Type-Options` 等。

### 10.4 性能与成本边界

服务端计算需保持在小候选集：

- 一个 token 默认加载不超过 8 个 reference feature sets。
- 每个特征集限制 ORB keypoints 上限，例如 1,000。
- query feature payload 限制总大小，例如 512 KB–1 MB，实际数值以协议编码和压测结果定。
- `/api/verify` 不接收、保存或转发原始图片。
- 大规模验证、高并发或全库搜索需求出现时，再评估专用计算服务；这不属于 v4.1 初期范围。

## 11. 实施阶段

### Phase 1：工程骨架与数据库

交付：

- Vite + React + TypeScript + TanStack Router/Query 工程。
- Vercel 静态 SPA 与最小 API 成功部署。
- Drizzle schema、迁移、数据库连通。
- 基础凭证状态机：`reserved → active → revoked/expired`。
- Token/passcode 生成、hash 与数据库唯一约束。

验收：

- 单仓库推送后，Preview 与 Production 均可访问 SPA 与 API。
- 数据库迁移可重复执行。
- 重复 token/passcode 不会激活两条 credential。

### Phase 2：创建端与特征协议

交付：

- 相机/文件输入。
- OpenCV.js Worker 加载与健康检查。
- 图像方向纠正、标准化预处理、ORB 特征提取。
- FeaturePayloadV1 编解码、Zod schema 校验。
- passcode reserve 与 credential finalize API。
- URL QR 与带覆盖层分享图生成、拖拽位置。

验收：

- 创建后数据库可读取到密语密文和 feature blob。
- 原始图特征与带二维码分享图逻辑分离。
- 长时间连续创建/拍摄不会出现明显 WASM 内存累积。

### Phase 3：读取端与服务端匹配

交付：

- QR 扫描及 URL token 读取。
- credential metadata 预检查。
- query feature 提取。
- Node.js Hamming KNN、ratio test 与 RANSAC matcher。
- `/api/verify`、审计记录与泛化失败响应。

验收：

- 同一视觉主体在合理缩放、旋转、轻度压缩后可通过。
- 不相关图像、空白图、特征不足图不能通过。
- 客户端修改 `matched: true` 或伪造 UI 状态无法取得密语。

### Phase 4：可靠性、安全与校准

交付：

- 限流、请求大小限制、失败审计与凭证过期/撤销。
- 真匹配/假匹配测试集。
- 阈值校准与性能压测。
- 移动端兼容性测试：iOS Safari、Android Chrome、桌面 Chrome/Firefox/Safari。
- 错误追踪、基础监控与隐私审查。

验收：

- 给出 FRR/FAR 的实测记录与当前阈值理由。
- 验证 API 在目标 Vercel 计划限制下稳定完成。
- 关键失败情形具有用户可理解的提示：QR 不可读、光线不足、图像纹理不足、凭证过期、验证失败。

## 12. 测试策略

### 12.1 视觉测试集

每个代表性参考主体应采集：

- 同一主体、不同距离与视角。
- 同一主体、不同光照和阴影。
- 截图、屏摄、社交平台压缩后的版本。
- 轻度/重度裁剪、旋转、模糊和局部遮挡。
- 相似但错误的对象或场景。
- 无纹理、纯色、完全错误图像。

### 12.2 分层测试

| 层级 | 测试重点 |
|---|---|
| 单元测试 | token hash、AEAD 加解密、feature codec、Hamming、KNN、ratio test、RANSAC |
| 契约测试 | 浏览器 Worker 输出能被 API schema 与 matcher 正确解析 |
| 集成测试 | reserve → finalize → meta → verify 成功/失败完整链路 |
| E2E 测试 | 摄像头权限、QR 扫描、创建下载、读取验证、撤销/过期 |
| 负载测试 | 高 descriptor 数、最大参考图数、并发 verify、冷启动 |
| 安全测试 | token 枚举、重复提交、payload 畸形、超大请求、伪造客户端状态 |

## 13. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| OpenCV.js bundle 缺少 ORB 或 API 与预期不符 | 特征提取阻塞 | 第一阶段即固定版本并建立浏览器端冒烟测试；必要时自行构建 bundle |
| OpenCV.js Worker 内存泄漏 | 移动端崩溃 | 所有 cv 对象显式 `delete()`；长时间拍摄回归测试；限制分辨率与 nFeatures |
| QR 叠加区域污染 ORB | 错误匹配或验证失败 | 原始参考图与分享图分离；overlay 模式使用 QR mask 与独立特征集 |
| 单参考图鲁棒性不足 | FRR 偏高 | 支持多参考图，收集真实视角/光照样本，采用 RANSAC 内点验证 |
| 相似纹理造成误匹配 | FAR 偏高 | ratio test + mutual check + RANSAC + 阈值校准，不单看 descriptor 数量 |
| 客户端伪造特征请求 | 未授权获取密语 | 后端独立匹配、token 限流、响应最小化、审计异常请求 |
| Vercel Function CPU/时长波动 | 验证超时或成本上升 | 限制特征规模和参考图数；避免原图上传；先压测后设置配置 |
| 数据库连接在 serverless 下不稳定 | API 故障 | 使用 serverless/HTTP Postgres driver；不要依赖进程内长期连接池 |
| 算法升级导致旧数据不可匹配 | 历史凭证失效 | feature schema、预处理和 matcher 全部版本化；保留旧 matcher 或安排迁移 |

## 14. v4.1 最终结论

本方案将项目定义为：

> 一个部署在单一 Vercel Project 上的视觉二次验证应用：浏览器通过 OpenCV.js 提取标准化 ORB 特征；Vercel Node.js Server Functions 从 PostgreSQL 读取绑定特征集，在服务端完成 Hamming、KNN、ratio test 和 RANSAC 的可信比对；验证成功后才返回服务端加密保存的密语。

该架构满足以下边界：

- 前端和后端代码统一在一个仓库维护并一次性部署至 Vercel。
- PostgreSQL 是唯一必需的外部数据服务。
- 图像不必上传到服务端，降低隐私、带宽与存储负担。
- 最终验证在服务端完成，避免客户端直接伪造放行结果。
- QR 与视觉特征各司其职：QR 快速定位凭证，视觉匹配实现二次验证。
- 架构保留多 Matcher 扩展能力，但 MVP 优先实现 `orb-hamming-ransac-v1`，避免过早引入 OpenCV server-side、全库检索或额外微服务。
