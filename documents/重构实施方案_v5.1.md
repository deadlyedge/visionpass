# 实施方案 v5.1（TanStack Start 全栈产品级演进：从 MVP 到正式商用）

## 0. 文档定位与演进目标

本方案是 VisionPass（视觉密语）项目从 **v5.0 最小可行性验证系统（MVP）** 全面演进为 **v5.1 正式商用产品** 的实施技术路线。

### 核心演进背景与设计哲学：
1. **坚守全栈现代化基座**：彻底巩固基于 **TanStack Start (Vite + Nitro + Bun + React 19)** 的现代全栈同构体系，全量采用类型安全的 **Server Functions (`createServerFn`)** 进行前后端通信，服务端代码收敛于 `src/server/`，享受编译时类型安全与 Nitro 统一打包。
2. **坚守零原图传输与存储**：原始图像严禁上传或持久化，所有视觉特征（ORB Keypoints & Descriptors）均在客户端提取，服务端仅存特征数据，杜绝隐私与存储开销风险。
3. **引入生产级安全防护体系**：升级为 **双 Token（publicToken + displayPasscode）** 与数据库哈希存储；密语升级为 **AES-256-GCM AEAD 服务端受控加密**；引入完整的状态机（`reserved` / `active` / `expired` / `revoked`）与请求防枚举/防重放机制。
4. **提升视觉算法工业级鲁棒性**：算法从基础暴力 Hamming 匹配演进为 **Hamming + KNN + Lowe Ratio Test + RANSAC Homography 几何一致性检验** 的纯 TypeScript 高性能比对器；抽象标准 `MatcherStrategy` 策略接口。
5. **打磨产品级端侧体验**：OpenCV.js 迁移至 **Web Worker** 避免主线程阻塞；支持移动端相机调起与二维码直接扫描；支持**带 QR 覆盖层的分享海报生成**（带 QR Mask 隔离）；保持**单参考图极简架构**，降低系统复杂度与交互负担。

### 1.2 严格遵循的技术铁律
1. **无独立 REST API / `api/` 目录**：所有的接口交互收敛为 `src/server/functions/*.ts` 中的 `createServerFn`。
2. **服务端无原生 C++/Python 依赖**：所有特征比对、几何投影校验均以高效 TypeScript（位运算、TypedArray、矩阵变换）实现，零冷启动开销。
3. **原图绝对不上云**：客户端仅传输紧凑特征 Payload；任何分享图生成完全在前端 Canvas 完成。
4. **单参考图极简闭环**：单凭证绑定单张高质量参考图特征，架构清晰，易于维护与快速匹配。
5. **参考原图与分享海报隔离**：主特征提取基于原始纯净参考图；若用户选择带二维码海报作为分享物，另建兼容特征集并对其应用 QR Mask，防止二维码图案干扰特征匹配。

## 2. 凭证安全模型与加密体系

### 2.1 凭证标识设计

| 标识 | 长度与格式 | 用途 | 安全与存储策略 |
|---|---|---|---|
| `publicToken` | CSPRNG 16 字节 (约 22 字符 Base64URL) | 核心能力令牌，嵌入 `/r/$token` URL 及 二维码中 | 数据库不存明文，仅保存 `HMAC-SHA-256(TOKEN_PEPPER, publicToken)` |
| `displayPasscode` | 10~12 位 Base32 易读字符串 | 调试、人工备用输入、展示码 | 数据库仅保存 `HMAC-SHA-256(TOKEN_PEPPER, displayPasscode)` |

### 2.2 密语加解密模型（AEAD）
- 使用标准 **AES-256-GCM** 算法。
- 环境变量 `SECRET_ENCRYPTION_KEY`（32 字节 Hex/Base64）存放在服务端安全环境变量中。
- 创建凭证时：生成 12 字节随机 IV，加密密语，产生 `secretCiphertext` 和 16 字节 `authTag`。
- 验证通过后：使用对应 IV 与 authTag 解密密文并返回，否则绝不解密。

### 2.3 凭证状态机

```text
  [ reserveCredentialFn ]
             │
             ▼
      ┌──────────────┐   超时未激活 (TTL 30m)
      │   reserved   │ ──────────────────────► [ expired ] (惰性清理/归档)
      └──────────────┘
             │
             │ [ finalizeCredentialFn ]
             ▼
      ┌──────────────┐   超过 expiresAt
      │    active    │ ──────────────────────► [ expired ]
      └──────────────┘
             │
             │ 手动撤销 / 异常风控
             ▼
      ┌──────────────┐
      │   revoked    │
      └──────────────┘
```

## 3. 图像处理与特征协议演进

### 3.1 客户端 Worker 图像预处理流水线
1. **读取与 EXIF 纠偏**：从 File/Blob 读取为 ImageBitmap/Canvas，根据 EXIF orientation 进行物理旋转归一化。
2. **尺寸归一化**：等比例缩放至最长边 $640\text{px}$（采用平滑插值）。
3. **灰度化与对比度增强**：转为灰度图（`cv.COLOR_RGBA2GRAY`），可选 CLAHE（自适应直方图均衡化，应对弱光/过曝环境）。
4. **QR 区域 Masking（可选）**：如果处理带二维码覆盖层的分享图，根据覆盖层矩形区域将该区域掩码置黑，排除二维码边缘干扰。
5. **ORB 提取**：提取最多 500 个特征点（Scale Factor: 1.2, Levels: 8, WTA_K: 2），获取关键点坐标与 32 字节描述子。
6. **紧凑编码**：通过 Transferable `ArrayBuffer` 与 Base64URL 序列化输出。

### 3.2 特征协议定义 (`FeaturePayloadV1`)

```ts
export type FeaturePayloadV1 = {
  version: 1;
  algorithm: "orb";
  image: {
    width: number;
    height: number;
    exifNormalized: true;
  };
  preprocessing: {
    grayscale: true;
    resizeLongEdge: 640;
    claheApplied?: boolean;
    qrMask?: {
      x: number; // 归一化 0~1
      y: number;
      width: number;
      height: number;
    };
  };
  orbConfig: {
    nFeatures: number;

  };

  };
};
```

## 4. 工业级服务端匹配器（Matcher Engine）

### 4.1 核心匹配策略体系

抽象出通用的 Matcher 策略接口：

```ts
export interface MatcherStrategy {
  readonly id: string;
  readonly supportedVersions: readonly number[];
  match(input: {
    query: FeaturePayloadV1;
    reference: FeaturePayloadV1;
  }): Promise<MatchResult>;
}

export type MatchResult = {
  matched: boolean;
  score: number;
  goodMatchCount: number;
  inlierCount: number;
  inlierRatio: number;
  reason:
    | "matched"
    | "insufficient_features"
    | "ratio_test_failed"
    | "homography_failed"
    | "below_threshold";
};
```

### 4.2 算法核心流程：`orb-hamming-ransac-v1`

1. **Hamming KNN 检索 (k = 2)**：
   - 对 query 中的每个描述子，在 reference 描述子集合中利用 Brian Kernighan 位运算计算 Hamming 距离，找出最近邻 $d_1$ 和次近邻 $d_2$。
2. **Lowe's Ratio Test**：
   - 过滤条件：$d_1 < \text{RATIO\_THRESHOLD} \times d_2$（推荐 $\text{RATIO\_THRESHOLD} = 0.75$）。只有通过比例测试的点才进入候选集（Good Matches）。
3. **Mutual Consistency Check（可选双向一致性）**：
   - 确认 query $\to$ ref 的匹配与 ref $\to$ query 的最近邻相互对应，排除多义性纹理。
4. **RANSAC 单应性矩阵（Homography）几何内点校验**：
   - 使用 RANSAC 算法对候选匹配点对 $(x_q, y_q) \leftrightarrow (x_r, y_r)$ 进行随机采样，拟合透视变换矩阵 $H$。
   - 计算重投影误差（Reprojection Error $< 3.0\text{px}$）的内点数（Inliers）。
5. **综合判定模型**：
   $$\text{Matched} = (\text{goodMatches} \ge 20) \land (\text{inliers} \ge 12) \land \left(\frac{\text{inliers}}{\text{goodMatches}} \ge 0.45\right)$$
   比对通过即判定为合法放行并解密密语。

## 6. Server Functions 通信协议定义

全部基于 TanStack Start `createServerFn` 实现：

### 6.1 `reserveCredentialFn`
- **Method**: `POST`
- **Input**: `{}` (无或可选过期时长配置)
- **Output**: `{ publicToken: string, displayPasscode: string, reserveExpiresAt: string }`
- **处理**:
  1. 生成 CSPRNG `publicToken` 与 `displayPasscode`。
  2. 计算两者的 HMAC-SHA-256 哈希。
  3. 在 `credentials` 表中插入 `status = 'reserved'` 记录，设置 30 分钟 TTL。
  4. 返回明文 Token 供客户端即时渲染与预备。

### 6.2 `finalizeCredentialFn`
- **Method**: `POST`
- **Input**:
  ```ts
  {
    publicToken: string;
    secret: string;
    feature: FeaturePayloadV1; // 单参考图特征
    qrOverlayMeta?: {
      x: number;
      y: number;
      width: number;
      height: number;
    };
  }
  ```
- **Output**: `{ success: boolean, readUrl: string }`
- **处理**:
  1. 计算 `publicToken` 哈希并查找处于 `reserved` 且未过期的记录。
  2. 使用 `SECRET_ENCRYPTION_KEY` 通过 AES-256-GCM 加密密语。
  3. 保存单张参考特征 `feature`。
  4. 事务提交：将凭证状态更新为 `active`，设置 `activatedAt`。

### 6.3 `getCredentialMetaFn`
- **Method**: `GET`
- **Input**: `{ tokenOrPasscode: string }`
- **Output**: `{ valid: boolean, requiresVisualVerification: boolean }`
- **处理**:
  1. 支持 `publicToken` 或 `displayPasscode` 的哈希查找。
  2. 仅在凭证存在且 `status === 'active'` 且未超时的情况下返回 `valid: true`。
  3. 绝不向前端泄露密语、参考图特征点及敏感审计数据。

### 6.4 `verifyCredentialFn`
- **Method**: `POST`
- **Input**: `{ tokenOrPasscode: string, feature: FeaturePayloadV1 }`
- **Output**: `{ matched: true, secret: string } | { matched: false }`
- **处理**:
  1. 限流与 Payload 尺寸安全检查（特征点数 20~500）。
  2. 根据 Token 哈希拉取凭证及其参考特征 `featurePayload`。
  3. 执行 `orb-hamming-ransac-v1` 匹配。
  4. 比对命中（Match 且 Inlier 达标）时：解密密语，记录审计日志 `result = 'matched'`，返回 `{ matched: true, secret }`。
  5. 否则：记录审计日志 `result = 'failed'`，返回 `{ matched: false }`。

## 7. 详细实施里程碑路线图

### 阶段 1：安全模型升级与数据库迁移 (Milestone 1)
- **任务项**：
  1. 更新 `drizzle/schema.ts`，引入 `public_token_hash`、`passcode_hash`、AEAD 密文存储与 `verification_attempts` 表。
  2. 在 `src/server/crypto/` 中实现 `tokens.ts`（HMAC-SHA-256 哈希生成）与 `secrets.ts`（AES-256-GCM 加解密工具）。
  3. 执行 Drizzle 数据库迁移与适配。
  4. 开发环境添加操作 log，便于追踪比对与解密过程。
  5. 统一常量保存位置（如 `src/lib/constants.ts`），方便集中微调匹配阈值与识别精度。
- **验收标准**：
  - 数据库中不出现任何明文 Token 与明文密语；加解密单元测试覆盖率 100%。

### 阶段 2：Matcher 策略体系与 RANSAC 算法演进 (Milestone 2)
- **任务项**：
  1. 建立 `src/server/matcher/types.ts` 与 `src/server/matcher/ransac.ts`（实现纯 TypeScript 的 2D 单应性矩阵变换与 RANSAC 采样器）。
  2. 实现 `orb-hamming-ransac-v1.ts`，包含 KNN 2-NN 检索、Lowe's Ratio Test 与内点比率评估。
  3. 编写仿真单元测试：测试正向形变图片（可通过）、相似建筑/错误物体（有效拒绝）、纹理缺失图（拦截）。
- **验收标准**：
  - 在无原生 C++ 依赖的前提下，RANSAC 算法单次匹配耗时在 15ms 内完成，拒绝率与内点判定稳定。

### 阶段 3：Web Worker 改造与端侧流水线升级 (Milestone 3)
- **任务项**：
  1. 创建 `src/workers/opencv.worker.ts`，将 OpenCV.js WASM 加载、EXIF 纠偏、长边缩放、CLAHE 灰度化与 ORB 提取全部移入 Worker。
  2. 实现客户端提取封装库 `src/lib/vision-worker-client.ts`，支持进度通知与 Promise 异步调用。
  3. 严格执行 WASM 内存清理机制（在 `finally` 块中对所有 `cv.Mat`、`cv.KeyPointVector` 调用 `.delete()`）。
- **验收标准**：
  - 图片上传处理期间，浏览器 UI 帧率保持 60fps，无任何阻塞卡顿；长耗时或连续提取无 WASM 内存泄漏。

### 阶段 4：产品级功能扩展 (Milestone 4)
- **任务项**：
  1. **带 QR 覆盖层分享图生成器**：在创建成功后，前端 Canvas 支持将 QR 码与参考图合成海报，支持用户拖拽摆放位置并导出高质图片；自动生成带 QR Mask 的兼容特征。
  2. **扫码与备用口令读取页**：升级 `/r/$token` 与 `/read` 路由，支持调起本地摄像头使用原生 `BarcodeDetector`（+ ZXing 备用）扫描二维码，并支持手动输入 `displayPasscode`。
- **验收标准**：
  - 用户可在手机端一键扫码拉起验证；海报导出正常；手动输入口令正常唤起验证页。

### 阶段 5：生产级加固、审计与一键部署 (Milestone 5)
- **任务项**：
  1. 在 Server Functions 中集成内存级/IP 级滑动窗口限流与请求大小限制。
  2. 验证审计日志记录（记录匹配分值、耗时、IP 哈希，不记录原图数据）。
  3. 配置 Vercel 部署环境与 Nitro 打包参数，配置完整安全响应头（CSP、HSTS、X-Content-Type-Options）。
  4. 全面端到端联调测试与 Biome 代码质量规范检查。
- **验收标准**：
  - `bun run build` 与 `bunx @biomejs/biome check` 零错误；一键成功部署至 Vercel，各项功能全链路通过。
