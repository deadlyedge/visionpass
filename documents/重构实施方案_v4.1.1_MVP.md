# 重构实施方案 v4.1.1（MVP：最小可验证模型）

## 0. 文档目的

本方案用于指导 AI 快速开发一个可部署、可验证、可迭代的最小版本。

目标不是一次完成完整视觉密语产品，而是在最少功能、最少依赖和最低部署复杂度下，验证以下核心闭环：

> 创建者上传一张参考图片并保存一条密语；系统生成一个 URL 二维码。读取者打开该 URL，上传同一张或高度相似的图片；浏览器提取 ORB 特征，Vercel Server Function 从 PostgreSQL 取出参考特征并进行比对；匹配成功后返回密语。

MVP 必须能以**一个 Git 仓库、一个 Vercel Project、一个 PostgreSQL 数据库**完成部署。

---

## 1. 范围控制

### 1.1 本版本必须实现

- React + Vite + TypeScript SPA。
- 使用bun管理包。
- TanStack Router 和 TanStack Query。
- 一个 PostgreSQL 数据库。
- Vercel Server Functions。
- 创建凭证：上传一张参考图片、填写密语。
- 浏览器端 OpenCV.js 提取 ORB features。
- 服务端保存参考 feature payload 到数据库。
- 生成包含读取 URL 的二维码。
- 读取凭证：打开 URL、上传验证图片、浏览器提取 ORB features。
- Vercel Function 从数据库读取对应 feature payload，完成基础 ORB descriptor 匹配。
- 匹配成功后返回密语；失败后返回失败提示。
- 可在 Vercel Preview / Production 环境完成完整演示。

### 1.2 本版本明确不做

以下功能全部延后，AI 不应主动扩展实现：

- 不做摄像头实时预览、连续扫码或拍照引导。
- 不做二维码扫描；MVP 只生成二维码，读取通过打开 URL 完成。
- 不做条形码、OCR、手动 passcode 输入。
- 不在图片中叠加二维码，不做拖拽二维码位置，不导出带码图片。
- 不做多张参考图；每个凭证只绑定 1 张参考图。
- 不做 pHash、dHash、FLANN、pgvector、向量数据库或全库图像检索。
- 不做 RANSAC、homography、几何校验、mutual check。
- 不做服务端 OpenCV.js 或原始图片上传至 API。
- 不做密语端到端加密、KMS、数据库字段加密。
- 不做账户、登录、协作、权限分级、凭证撤销、过期、分享控制。
- 不做 Redis、队列、对象存储、文件持久化或独立后端服务。
- 不做复杂速率限制、审计日志、监控平台接入。
- 不做移动端兼容性优化以外的原生 App 支持。

> 注意：本版本用于验证技术链路与基本体验，不应被视为安全方案。URL token 是可转发的访问凭证；仅靠 ORB descriptor 基础比对不足以防御恶意伪造或相似图误匹配。

## 2. 成功标准

完成后应可以进行以下演示：

1. 访问 `/create`。
2. 上传一张具有明显纹理/建筑/物体结构的图片，输入密语。
3. 点击“创建凭证”。
4. 页面显示读取 URL 和对应二维码。
5. 在新标签页打开读取 URL，例如 `/r/<token>`。
6. 上传创建时的同一张图片。
7. 页面显示“验证通过”及密语。
8. 上传明显无关的图片。
9. 页面显示“验证失败”，且不显示密语。
10. 整套流程部署在 Vercel，数据只存外接 PostgreSQL。

MVP 的通过标准是“同图上传稳定通过、明显无关图稳定失败”，而不是解决真实物体的多角度、屏摄、遮挡、低光和复杂欺骗问题。

## 3. 最小架构

```text
┌─────────────────────────────────────────────────────┐
│ Vercel Project                                       │
│                                                     │
│  Vite + React SPA                                   │
│  ├─ /create                                         │
│  ├─ /r/:token                                       │
│  ├─ OpenCV.js（浏览器主线程，MVP 可不用 Worker）       │
│  ├─ 图片上传后提取 ORB feature payload                │
│  └─ 本地生成 URL QR                                 │
│                                                     │
│  Vercel Node.js Server Functions                    │
│  ├─ POST /api/credentials                            │
│  ├─ GET  /api/credentials/:token                     │
│  └─ POST /api/verify                                 │
└───────────────────────┬─────────────────────────────┘
                        │
                        ▼
            ┌───────────────────────────┐
            │ PostgreSQL                 │
            │ credentials                │
            │ - token                    │
            │ - secret                   │
            │ - feature JSON/blob        │
            └───────────────────────────┘
```

### 3.1 关键简化

- 前端与 API 同仓库、同 Vercel Project。
- 图片只在浏览器中解码和提取特征，不上传也不保存原图。
- OpenCV.js 只在浏览器端运行。
- 后端只处理压缩后的 feature payload 并完成基础 Hamming matching。
- 每个 token 精确匹配数据库中一条 credential，因此没有全库视觉搜索。
- 初期允许 descriptor 数据以 JSON/Base64 存储，优先快速跑通；后续再迁移到 `BYTEA` 二进制编码。

## 4. 技术选型

| 领域 | MVP 选择 | 说明 |
|---|---|---|
| 前端 | React + Vite + TypeScript | 轻量 SPA，适合 Vercel 静态部署 |
| 路由 | TanStack Router | `/create` 与 `/r/$token` 两个核心路由 |
| 请求与状态 | TanStack Query | 管理创建、读取元数据和验证请求 |

| API | Vercel Node.js Functions | 放在 `api/` 目录 |

- Prisma、Supabase SDK、Firebase SDK。
- Docker、Python、FastAPI、OpenCV Node native bindings。
- Redis、BullMQ、S3 SDK、消息队列。
- pgvector、向量数据库、机器学习 embedding 模型。
- 完整状态管理库（Redux、Zustand）——除非项目已有且已使用。

## 5. 路由与页面

### 5.1 `/create`

用途：创建一个视觉密语凭证。

页面元素：

- 标题与简短说明。
- 图片文件选择器，仅接受 `image/*`。
- 已选图片的预览。
- 密语 `textarea`。
- “提取图像特征并创建”按钮。
- OpenCV 加载、特征提取、网络提交过程状态。
- 创建成功后显示：
  - 读取链接。
  - URL 二维码。
  - 复制链接按钮。
  - “打开读取页”按钮。

交互规则：

- 未选择图片或密语为空时，禁止提交。
- 若提取到的 ORB keypoint 数量过少，显示“图片纹理不足，请换一张更清晰、有结构的图片”。
- 创建成功后不要再次提交同一个表单；显示成功结果并提供“创建新的凭证”。

### 5.2 `/r/$token`

用途：读取并验证对应凭证。

页面元素：

- 凭证状态提示（“请上传与原图相符的图片进行验证”）。
- 图片文件选择器。
- 已选验证图片预览。
- “验证并读取密语”按钮。
- 特征提取、服务端验证过程状态。
- 验证成功时显示密语。
- 验证失败时显示泛化提示：“图片未能通过验证，请使用与参考视觉主体一致的图片重试。”

交互规则：

- 路由加载时先查询 token 是否存在。
- token 无效时显示“凭证不存在或链接无效”，不展示上传表单。
- 密语只在验证成功后的响应中显示，不在 metadata API 中返回。

## 6. 数据库设计

MVP 只需要一个表。

```ts
// server/db/schema.ts
export const credentials = pgTable("credentials", {
  id: uuid("id").defaultRandom().primaryKey(),
  token: varchar("token", { length: 64 }).notNull().unique(),
  secret: text("secret").notNull(),
  featurePayload: jsonb("feature_payload").notNull(),
  createdAt: timestamp("created_at", { withTimezone: true })
    .defaultNow()
    .notNull(),
});
```

### 6.1 MVP 数据取舍

为缩短开发时间，MVP 可直接保存：

- `token` 明文。
- `secret` 明文。
- `featurePayload` JSONB。

这是明确的 MVP 妥协，仅用于受控演示环境。生产版本必须至少升级为：

- token 哈希存储。
- 密语加密存储。
- descriptor/keypoint 的二进制 blob 编码。
- 凭证状态、过期和限流。

### 6.2 token 生成

在 `POST /api/credentials` 的服务端使用 CSPRNG：

```ts
import { randomBytes } from "node:crypto";

const token = randomBytes(16).toString("base64url");
```

要求：

- 不能使用 `Math.random()`。
- token 碰撞时捕获数据库唯一约束错误后重试生成。
- 前端不自行生成最终 token。

## 7. 特征协议（MVP）

### 7.1 目标

协议必须足够简单，让前后端能稳定交换 descriptor 与 keypoint；不追求 v4.1 的完整兼容和二进制优化。

### 7.2 TypeScript 类型

```ts
export type OrbFeaturePayloadV1 = {
  version: 1;
  algorithm: "orb";
  imageWidth: number;
  imageHeight: number;
  descriptorSize: 32;
  keypoints: Array<{
    x: number;
    y: number;
  }>;
  descriptorsBase64: string;
};
```

约束：

- 图片一律在浏览器缩放到固定最长边 `640 px` 后再提取。
- 一律转为灰度图后提取。
- ORB `nfeatures` 固定为 `300`。
- `descriptorsBase64` 解码后长度必须满足：

```text
keypoints.length × descriptorSize
```

- 设置 `MIN_KEYPOINTS = 100`。小于该数量时客户端不提交。
- 服务端再次检查最大数量，例如 `MAX_KEYPOINTS = 500`。

### 7.3 浏览器端提取伪代码

```ts
async function extractOrbFeatures(file: File): Promise<OrbFeaturePayloadV1> {
  const image = await loadImageAndNormalizeOrientation(file);
  const canvas = resizeToLongEdge(image, 640);

  const src = cv.imread(canvas);
  const gray = new cv.Mat();
  const keypoints = new cv.KeyPointVector();
  const descriptors = new cv.Mat();

  try {
    cv.cvtColor(src, gray, cv.COLOR_RGBA2GRAY);

    const orb = new cv.ORB(500);
    orb.detectAndCompute(gray, new cv.Mat(), keypoints, descriptors);

    return encodeOrbPayload({
      width: gray.cols,
      height: gray.rows,
      keypoints,
      descriptors,
    });
  } finally {
    src.delete();
    gray.delete();
    keypoints.delete();
    descriptors.delete();
  }
}
```

实现注意：

- OpenCV.js 的具体构造器与 API 必须以实际所用版本验证；不要直接假设 Python `cv2` API 可用。
- `orb` 和临时 mask `Mat` 也必须在实际实现中释放。
- 初期可将处理放在前端主线程，以减少 Worker bundling 复杂度；页面必须展示处理状态。
- 若主线程卡顿明显，再将完全相同的提取逻辑迁移到 Web Worker，协议不变。

## 8. API 设计

API 保持最少的三个端点。

### 8.1 `POST /api/credentials`

创建凭证。

请求：

```ts
type CreateCredentialRequest = {
  secret: string;
  feature: OrbFeaturePayloadV1;
};
```

响应：

```ts
type CreateCredentialResponse = {
  token: string;
  readUrl: string;
};
```

服务端逻辑：

1. 用 Zod 校验密语与 feature payload。
2. 限制密语长度，例如 1–1,000 字符。
3. 校验 keypoint 数为 20–500。
4. 解码并检查 `descriptorsBase64` 字节长度。
5. 生成 token，写入数据库。
6. 返回绝对读取 URL：`${APP_ORIGIN}/r/${token}`。

### 8.2 `GET /api/credentials/:token`

读取元数据，不返回密语。

响应：

```ts
type CredentialMetaResponse = {
  exists: boolean;
};
```

服务端逻辑：

- 只根据 token 查询 `id`。
- token 不存在统一返回 `{ exists: false }`，HTTP 可使用 404。
- token 存在返回 `{ exists: true }`。

### 8.3 `POST /api/verify`

验证图片特征并决定是否返回密语。

请求：

```ts
type VerifyRequest = {
  token: string;
  feature: OrbFeaturePayloadV1;
};
```

成功响应：

```ts
type VerifySuccessResponse = {
  matched: true;
  secret: string;
};
```

失败响应：

```ts
type VerifyFailureResponse = {
  matched: false;
};
```

服务端逻辑：

1. 校验 token 与 query feature。
2. 根据 token 取出 `featurePayload` 与 `secret`。
3. 对 query 与 reference 执行基础匹配。
4. 分数达到 MVP 阈值时返回密语。
5. 否则只返回 `{ matched: false }`。

## 9. MVP 匹配实现

### 9.1 原则

后端不使用 OpenCV.js；只实现最必要的 ORB descriptor 比对。

ORB descriptor 是字节数组。两个 descriptor 的 Hamming 距离等于每个字节 XOR 后，所有 bit 为 1 的数量之和。

```ts
export function hammingDistance(a: Uint8Array, b: Uint8Array): number {
  let result = 0;

  for (let i = 0; i < 32; i++) {
    let value = a[i] ^ b[i];
    while (value !== 0) {
      value &= value - 1;
      result++;
    }
  }

  return result;
}
```

### 9.2 匹配规则

对 query 中每个 descriptor：

1. 遍历 reference descriptors，找出最小距离 `bestDistance`。
2. 若 `bestDistance <= MAX_HAMMING_DISTANCE`，算作一个 good match。
3. 使用 good match 数量作为 MVP score。

初始常量：

```ts
const DESCRIPTOR_SIZE = 32;
const MAX_HAMMING_DISTANCE = 50;
const MIN_GOOD_MATCHES = 25;
```

成功条件：

```ts
matched = goodMatchCount >= MIN_GOOD_MATCHES;
```

### 9.3 重要限制

该算法是故意简化的 MVP：

- 不做 KNN ratio test。
- 不做 cross-check。
- 不做 RANSAC / homography。
- 不验证 keypoint 的几何分布。
- 因此容易被重复纹理、相似画面、伪造 descriptor 或阈值不当影响。

AI 必须将匹配器写成独立模块，例如：

```text
server/matcher/orb-basic.ts
```

接口应保持可替换：

```ts
export type MatchResult = {
  matched: boolean;
  goodMatchCount: number;
};

export function matchOrbBasic(
  query: OrbFeaturePayloadV1,
  reference: OrbFeaturePayloadV1,
): MatchResult;
```

后续 v4.2 可在不改 API 的情况下替换为：

```text
Hamming KNN → Lowe ratio test → RANSAC homography → 多参考图择优
```

### 9.4 性能边界

最坏情况下，500 × 500 × 32 的暴力 Hamming 比较约 800 万个字节级操作。对于单 token、单 reference 的 MVP 通常可以在 Node.js Function 中完成。

必须限制：

- `MAX_KEYPOINTS = 500`。
- `descriptorSize = 32`。
- 创建与验证请求体最大大小，例如 512 KB。
- 每个 token 一条 reference feature payload。

不要在循环中创建大量 `Uint8Array.slice()`；应通过 offset 访问同一块解码后的 descriptor buffer，减少分配。

## 11. 实施顺序

AI 必须按以下顺序实现，每完成一步都应确保构建、类型检查和基本运行不回归。

### Step 1：初始化与可部署空壳

- 建立 Vite + React + TypeScript 项目。
- 配置 TanStack Router：`/create` 和 `/r/$token`。
- 配置 Vercel，使 SPA 路由刷新不返回 404。
- 添加一个最小 health API，例如 `GET /api/health`。
- 部署 Vercel Preview 验证。

验收：

- `/create` 正常访问。
- 直接访问和刷新 `/r/demo-token` 均能打开 SPA 页面。
- `/api/health` 返回 JSON。

### Step 2：数据库与创建 API

- 配置 PostgreSQL `DATABASE_URL`。
- 用 Drizzle 建立 `credentials` 表和 migration。
- 实现 `POST /api/credentials`，暂时允许传 mock feature。
- 使用 curl/HTTP 客户端验证写入与响应 readUrl。

验收：

- 数据库出现一条 credential。
- API 返回 token 与正确 readUrl。

### Step 3：前端图片与 OpenCV 特征提取

- 将经过验证的 OpenCV.js/WASM 静态文件放入 `public/opencv/`。
- 实现一次性加载器，确保 `cv.onRuntimeInitialized` 后才可用。
- 实现上传、预览、最长边 640 resize、灰度化、ORB(500)。
- 实现 descriptor base64 编码与 `OrbFeaturePayloadV1`。
- 对 keypoint 太少的图片显示错误。

验收：

- 控制台或开发 UI 可显示 keypoint 数量、descriptor 字节数。
- 对同一图重复提取时，结构有效、尺寸一致。
- 页面无明显持续 WASM 内存增长；临时 Mat 被释放。

### Step 4：完成创建页面

- 接入 TanStack Query mutation。
- `/create` 提交 `secret + feature`。
- 创建成功后本地生成读取 URL 的二维码。
- 显示可复制链接与跳转按钮。

验收：

- 从上传图片到二维码显示可完整走通。
- 原始图片不进入 API 请求 body。

### Step 5：读取页与 metadata API

- 实现 `GET /api/credentials/:token`。
- `/r/$token` 页面加载时查询 metadata。
- 无效 token 显示错误；有效 token 显示上传与验证界面。

验收：

- 改造 URL token 后读取页不能进行验证。
- metadata 响应不含 secret 或 feature payload。

### Step 6：服务端匹配与验证 API

- 实现 feature payload 的服务端 Zod 校验与 Base64 长度检查。
- 实现 `server/matcher/orb-basic.ts`。
- 实现 `POST /api/verify`。
- `/r/$token` 上传图后提交 query feature 并按响应显示密语/失败。

验收：

- 同一参考图上传成功返回密语。
- 明显无关图不返回密语。
- API 不接受超过上限的 keypoint 数、错误 descriptor 长度或畸形 base64。

### Step 7：部署回归与最少保护

- 配置 Vercel 环境变量 `DATABASE_URL` 与 `APP_ORIGIN`。
- Preview 和 Production 各跑一次完整创建/读取演示。
- 对 API 添加基本 body size 限制和错误处理。
- 确保浏览器控制台、Vercel logs 中不记录 secret、完整 token 或 descriptor 内容。

验收：

- 在生产域名上从创建到验证完整可用。
- 无需手动部署第二个服务。

## 12. AI 开发约束

以下要求优先级最高：

1. 先跑通闭环，再做优化；不得因为“更安全、更通用、更优雅”而延迟 MVP。
2. 保持 TypeScript 严格模式；API 输入必须做 Zod 校验。
3. 不上传、不存储原始图片；API 只传 feature payload。
4. 后端自行计算 `matched`，前端只显示结果。
5. 不把 OpenCV.js 放进 Vercel Function。
6. 不实现 v4.1.1 范围之外的功能。
7. 每个 API 返回清晰、最小的 JSON；不泄露 secret、特征集、匹配细节。
8. 在错误路径也释放浏览器端 OpenCV 的临时对象。
9. 所有阈值集中定义为常量，不能散落在 UI 或 API 中。
10. matcher 必须独立模块化，方便后续替换为 ratio test/RANSAC 版本。

## 14. 已知限制与下一版方向

v4.1.1 的价值在于验证“图像特征 → 数据库存储 → Server Function 比对 → 条件返回密语”的链路，而不是保证现实环境下的高精度视觉认证。

MVP 常见预期问题：

- 对同一图经过严重压缩、裁剪、旋转或屏摄后，可能失败。
- 对重复纹理、相似图、同类建筑/物体，可能出现误匹配。
- 直接存 JSONB/Base64 会比二进制 blob 占用更多数据库与传输空间。
- token 和 secret 明文存储不适合公开生产环境。
- OpenCV.js 初始化会让首次操作有明显等待。

在 MVP 验证通过后，建议按收益排序升级：

1. 浏览器端 OpenCV.js 迁入 Web Worker，改善页面响应。
2. 参考图扩展为多张，并对各 feature set 取最佳匹配结果。
3. 后端引入 KNN + Lowe ratio test。
4. 引入 RANSAC homography 和内点率阈值，降低误匹配。
5. Feature payload 迁移到 `BYTEA` 紧凑二进制格式。
6. token 改为 hash 存储，secret 改为 AES-GCM 加密。
7. 加入凭证状态、过期、撤销和速率限制。
8. 增加 QR 扫描、相机拍摄及更完整的移动端体验。

## 15. 最终定义

v4.1.1 MVP 是一个最小的、可在 Vercel 快速部署的视觉密语演示系统：

> 使用浏览器端 OpenCV.js 从参考图和验证图提取标准化 ORB 特征；使用 Vercel Node.js Server Function 从 PostgreSQL 取得对应参考特征，执行基础 Hamming 距离匹配；达到阈值后才将该凭证关联的密语返回给读取者。

只要完成“创建一条凭证、生成 URL QR、打开 URL 上传同图、服务端匹配并返回密语、上传无关图失败”这一个闭环，即视为本版本成功。
